Cuando empiezo a trabajar en un sistema backend, rara vez pienso primero en la tecnología.

Lo primero que intento entender es el problema.

## 1. Entender el problema

Antes de hablar de arquitectura o herramientas, me hago preguntas como:

- ¿Qué está entrando en el sistema?
- ¿Qué debe salir?
- ¿Qué restricciones existen?
- ¿Qué partes pueden fallar?

Esto es más ingeniería de sistemas que programación.

## 2. Dividir el sistema

Una vez entiendo el problema, intento descomponerlo en piezas más pequeñas:

- servicios
- responsabilidades
- flujos de datos

La clave aquí no es la tecnología, sino la separación de responsabilidades.

## 3. Pensar en el tiempo

Un sistema no es estático.

Me interesa mucho cómo evoluciona:

- qué pasa cuando crece el volumen de datos
- qué ocurre cuando cambian los requisitos
- qué partes serán difíciles de modificar en el futuro

## 4. Elegir tecnología después

Solo en este punto tiene sentido hablar de herramientas:

- Java o Kotlin
- SQL o NoSQL
- monolito o microservicios

La tecnología es la última decisión, no la primera.

## Conclusión

He aprendido que la calidad de un sistema no depende tanto del lenguaje o framework usado, sino de cómo se ha pensado su estructura desde el principio.
